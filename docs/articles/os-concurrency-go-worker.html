一、进程、线程与用户态协程的本质区别

Linux 内核并不严格区分进程与线程，均以 task_struct 描述，底层统一调用 clone(2) 创建。 二者的本质差异由标志位决定：是否共享虚拟地址空间（CLONE_VM）、文件描述符表（CLONE_FILES）与信号处理表（CLONE_SIGHAND）。

维度 进程（Process） 线程（Thread） 协程（Coroutine / Goroutine）
核心角色 资源分配最小单位，独立页表 mm_struct CPU 调度最小单位，共享进程堆与 FD 用户态轻量级执行流，由 Runtime 调度
栈开销 独立虚拟地址空间 2MB–8MB 固定栈 Go 初始 2KB，按需动态扩缩
切换成本 微秒级 + 重载 CR3 → TLB Flush + Cache Miss 微秒级（内核态切换，不切页表） 纳秒级（纯用户态切 SP/PC）
崩溃影响域 硬件页表隔离，不影响兄弟进程 未捕获错误直接拖垮整个进程 未捕获 panic 直接拖垮整个进程

在语言选型上，Python 受 GIL（全局解释器锁）限制：CPU 密集型任务走 multiprocessing，高并发网络 I/O 走 asyncio； 而 Go 原生内置 Goroutine 与 GMP 调度器，以同步写法即可获得异步高并发性能，少量 OS 线程就能承载十万级协程。

二、Go GMP 调度模型核心机制

Go 调度器由三要素协作：G（Goroutine）携带执行栈与状态；M（Machine）是 OS 内核线程； P（Processor）是逻辑处理器（默认等于 CPU 核数 GOMAXPROCS），持有无锁本地队列 LRQ（容量 256） 与内存缓存 mcache。

  • 查找顺序与 Work Stealing：当 P 本地队列为空时，findrunnable() 按 LRQ → GRQ（每 61 次抽查防饿死）→ NetPoller → Work Stealing（从其他繁忙 P 尾部窃取一半 G） 寻找任务。
  • 同步阻塞 Syscall / CGO 的 Handoff 机制：网络 I/O 由 NetPoller（epoll/kqueue）异步接管，不阻塞 M；若发生慢文件 I/O 或 CGO 同步阻塞，sysmon 会把 P 从阻塞的 M1 剥离并交接给备用 M2，防止浪费 CPU 核。但大量并发阻塞 CGO 会持续推高 M 线程数（受 SetMaxThreads 限制，默认 10000）。

三、Go Worker 任务认领与防脏写（Fencing Token）

协程虽轻量，但无节制 go func() 会引发内存暴涨与下游雪崩。在生产级 Worker 池中，除了使用固定数量 Worker + 有界 Channel + context.Context 取消形成背压外，多 Worker 异步任务队列还必须解决「重复认领」「崩溃回收」与「假死苏醒后的迟到脏写」三大问题： 

-- 1. 原子条件认领：写入租约 lease_until 与递增版本号 version (Fencing Token)
UPDATE tasks
SET status = 'RUNNING', owner = $1, version = version + 1, lease_until = NOW() + INTERVAL '30 seconds'
WHERE id = $2 AND status = 'PENDING';

-- 2. 超时回收：原 Worker 崩溃或长 GC 未续租，新 Worker 携带旧 version 接管并再次递增 version
UPDATE tasks
SET owner = $1, version = version + 1, lease_until = NOW() + INTERVAL '30 seconds'
WHERE id = $2 AND status = 'RUNNING' AND lease_until <= NOW() AND version = $3;

-- 3. CAS 条件提交结果：假死苏醒的旧 Worker 持旧 version 提交时影响行数为 0，直接拦截脏写
UPDATE tasks
SET status = 'DONE', result = $1
WHERE id = $2 AND version = $3;

四、Context 超时取消、Linux 进程树清理与四大踩坑

在构建 codeos-runtime 断网代码执行器时，最容易出生产事故的不是语法，而是跨协程 Panic 击穿进程与超时后孤儿孙进程逃逸：

坑点 1：主协程 defer recover() 拦不住子协程 panic

panic 只沿当前 Goroutine 调用栈向上展开。必须在每个 Worker 入口最外层独立封装 defer recover()，打印堆栈并收敛为 error。

坑点 2：exec.CommandContext 超时残留孤儿孙进程 / 卡死管道

默认超时只杀直接子进程（如 sh），孙进程（如 sleep 60）被 PID 1 收养并继续占用 stdout 管道。正确做法是设置 Setpgid: true，超时向负 PGID（-pid）发 SIGKILL，配合 PR_SET_CHILD_SUBREAPER 与 cmd.Wait() 实现零残留、零僵尸。

五、后端面试高频追问（6 题精要答法）

  1. 为什么跨进程切换比同进程线程切换慢得多？

    跨进程切换必须重载页表基址寄存器（CR3），导致 TLB Flush 与 L1/L2/L3 CPU Cache 大面积失效；同进程线程共享页表，只做内核态上下文切换，保留了 TLB 与大部分热缓存。

  2. Go 协程初始栈只有 2KB，为什么生产环境仍要使用 Worker Pool？

    协程栈廉价但业务上下文、网络连接池与下游资源并不廉价。无界起协程会迅速耗尽堆内存、打爆下游依赖，且失去背压与优雅停机边界。

  3. Goroutine 死循环或长时间阻塞在 CGO 时，GMP 调度器会怎样？

    纯 Go 死循环自 Go 1.14 起可被 sysmon 发送 SIGURG 信号异步抢占；阻塞在 CGO/同步 Syscall 时，sysmon 会把 P 从阻塞 M 上剥离（Handoff）交给备用 M，但大量并发阻塞 CGO 会导致 OS 线程数飙升。

  4. exec.CommandContext 为什么会杀不干净？Setpgid 与 subreaper 分别解决什么？

    默认超时只杀直接子进程，孙进程逃逸并继续持有管道导致 CombinedOutput() 卡死。Setpgid: true + Kill(-pgid, SIGKILL) 一次性清理整组进程；subreaper 兜底收养脱离父进程的孤儿并由执行器统一 wait 回收防僵尸。

  5. 如何设计防重复认领、宕机自动恢复且拦截迟到脏写的异步任务队列？

    三板斧：原子条件更新抢占（WHERE status='PENDING'）+ 租约超时回收（lease_until）+ 单调递增版本号 Fencing Token（回写做 WHERE version=? CAS 校验）。

  6. 生产级 Worker 框架如何优雅处理 panic 与停机？

    每个 Worker 启动时统一套一层 defer recover() 将崩溃收敛为错误日志与告警指标；停机时关闭入口 Channel、取消根 context，再通过 sync.WaitGroup.Wait() 在宽限期内等待在途任务收尾。
